How the rewrite works

From a Windows .exe to Rust running inside Node

This is the long version — what actually changed under the hood when the six algorithms moved off C++ binaries and onto WebAssembly, and a proper walkthrough of each algorithm with a worked example, so the code stops being a black box.

Background

Why this changed

The /perform-algo route used to shell out to a compiled C++ program — one .exe per algorithm — that read the graph from server/file io/input.txt and wrote its step-by-step trace to server/file io/output.txt.

Two things made that unworkable as a real, deployed app:

  • The binaries only run on Windows. A production server is essentially always Linux, and a Windows .exe simply won't execute there — full stop.
  • Every request shared the same two files. There was one input.txt and one output.txt for the entire server. Two people running the visualizer at the same moment would silently overwrite each other's graphs.

The fix addresses both at once: every algorithm is now a Rust function, compiled to WebAssembly, and loaded straight into the Node.js process. There's no external program to spawn and no file to share — a request comes in, the algorithm runs entirely in memory using only that request's own data, and a response goes out. Nothing is left behind for the next request to trip over.

Background

What WASM actually is

WebAssembly (WASM) is a compact binary instruction format that runs at close to native speed, inside a sandbox. It was originally built so browsers could run heavy code fast, but Node.js can load and execute .wasm files directly too — no browser required. That's what makes running Rust inside the Express server possible at all.

Rust compiles to WASM cleanly because it has no garbage collector and no runtime to drag along — the output is small and fast. Two tools make the Rust ↔ JavaScript boundary usable:

  • wasm-bindgen — generates the "glue" that lets JavaScript call a Rust function and hand it real data (arrays, numbers, strings), not just raw bytes.
  • wasm-pack — the build tool that runs the whole pipeline: compile Rust for the wasm32 target, run wasm-bindgen over the output, and produce a ready-to-use package.

Running wasm-pack build --target nodejs --release inside server/rust_algos/ produces server/rust_algos/pkg/, which contains:

FileWhat it is
graphpathguru_algos_bg.wasmThe actual compiled Rust — a binary, not readable text.
graphpathguru_algos.jsThe generated JS wrapper: plain functions like run_dijkstra(v, adj, source) that internally load the .wasm and hand your arguments across the boundary.
graphpathguru_algos.d.tsTypeScript type definitions for the same functions.
Why the compiled output is committed to git Exactly like the old .exe files were checked in, the compiled pkg/ folder is committed too. That means the deployed server never needs Rust or wasm-pack installed — it just needs Node, and it require()s the pre-built module like any other npm package. You only rebuild when you actually change algorithm logic in one of the .rs files.
Background

One request, start to finish

Concretely, here's everything that happens between you clicking Save and the results panel updating, for Dijkstra specifically — the other five follow the same shape.

  1. Browser → Express. Home.jsx sends { nodes, edges, algoID, source, destination } as JSON.
  2. Build the adjacency list. buildGraph() turns the React Flow nodes/edges into adj[i] = [[neighbor, weight], ...] — plain nested arrays.
  3. Cross into WASM. algos.run_dijkstra(V, adj, source) is called. serde-wasm-bindgen deserializes that JS array straight into Rust's Vec<Vec<(usize, i32)>> — no manual parsing needed on either side.
  4. Rust runs the algorithm. As it runs, it builds up one big string recording every step — who got compared to whom, and whether the comparison improved anything. That's the same "tagged" format the original C++ used, kept on purpose so the existing frontend animation logic didn't need to change.
  5. The string comes back as a plain JS string. No object, no class — just text.
  6. JavaScript parses it. parseGenericOutput() (or the Floyd/Johnson/Yen-specific variant) runs regexes over that string to build the JSON the frontend actually wants: result, checkNode, distance, curr_node, and now also shortestPath.
  7. One response, done. Express sends it all back in a single JSON object, and the browser both saves it to history and animates it.

What that tagged string looks like

Trimmed example, for the 2-node graph 0 → 1 (weight 5), source 0:

<ds>
	0,0
	0 INF
	-1 -1
</ds>
<adj>
	0, 0:
	1, 5, 1, 0, 5
</adj>
<result>
	1000 2 1 0
	-1 0
	0 5
</result>

<ds> is a snapshot of the algorithm's internal state at that step (its queue, its distances so far, its predecessors) — that's what drives the "compare" label you see mid-animation. <adj> records one node's outgoing edges being checked, and whether each one improved anything (the 1/0 flags). <result> is the final summary: time taken, node count, edge count, source, then the predecessor and distance arrays. It's not pretty, but it's exactly what the frontend was already built to parse, so keeping it meant the six-file animation layer needed zero rewrites.

Where everything lives

server/rust_algos/src/dijkstra.rs
The shared, full-traversal Dijkstra core. Reused three ways: as-is for algorithm 1, wrapped with path reconstruction for Yen, and re-tagged (<ds2>/<adj2>) inside Johnson's per-source loop.
server/rust_algos/src/bellman_ford.rs
The edge-relaxation core, reused as-is for algorithm 2 and again (with a virtual source node) as Johnson's reweighting pass.
server/rust_algos/src/spfa.rs
The queue-based relaxation used by algorithm 3.
server/rust_algos/src/floyd_warshall.rs
The all-pairs DP for algorithm 4, plus the successor-matrix path reconstruction added alongside it.
server/rust_algos/src/johnson.rs
Wires the Bellman-Ford reweighting pass into V calls to the Dijkstra core, one per source node.
server/rust_algos/src/yen.rs
Runs Dijkstra repeatedly, removing the previous path's edges each time, to find k distinct shortest paths.
server/rust_algos/src/lib.rs
The six #[wasm_bindgen] entry points — run_dijkstra, run_bellman_ford, etc. — the only functions JavaScript can actually call.
server/index.js
Builds the adjacency list, calls the right WASM function for the chosen algorithm, parses its output, reconstructs the shortest path, and returns everything as one response.
The algorithms

One example graph, used throughout

To make the six algorithms comparable, every section below starts from the same small graph — 4 nodes, 5 directed edges, source node 0, destination node 3.

1

Dijkstra

Handles negative weightsNo
Findssource → all nodes
TimeO((V+E) log V)
Rust filedijkstra.rs

Dijkstra is greedy: always expand whichever known-reachable node currently has the smallest distance, on the logic that once you've popped a node with the smallest distance in the queue, nothing still in the queue can possibly offer it a cheaper route later. That guarantee only holds if edge weights are non-negative — a negative edge could undercut a "final" distance after the fact, which is exactly why Bellman-Ford and SPFA exist for graphs that need it.

The mechanism is a min-priority queue, ordered by distance:

  1. Seed the queue with (distance 0, source). Every other node starts at infinity.
  2. Pop the smallest-distance entry. Its distance is now final.
  3. For each of its outgoing edges, check whether going through this node beats the neighbor's current best distance. If so, update it and push the neighbor back onto the queue.
  4. Repeat until the queue is empty.

Stale queue entries for node 1 (dist 4) and node 3 (dist 6) get popped too, but change nothing — this is the same lazy-deletion behavior the original C++ had, and it's why you sometimes see a node get compared more than once in the animation.

Result: dist = [0, 2, 1, 3], shortest path 0 → 2 → 1 → 3, total weight 3. Notice node 1's distance was corrected from 4 down to 2 mid-run — that's the moment the animation colors it blue again after it already looked settled.

In the animation Red is the node just popped off the queue; blue is the neighbor being checked against it; green means that check just improved a distance, black means it didn't. The gold highlight that appears at the end traces the actual winning path — here, 0 → 2 → 1 → 3.
2

Bellman-Ford

Handles negative weightsYes
Findssource → all nodes
TimeO(V · E)
Rust filebellman_ford.rs

Where Dijkstra is clever about which edge to check next, Bellman-Ford is deliberately dumb: it checks every single edge, in whatever order they were given, and repeats that full pass V - 1 times. That's less efficient, but it comes with a real advantage — it never assumes a distance is final until it's actually done, so it works correctly even with negative edge weights, and after those V-1 passes it can run one more pass to check whether anything can still improve. If it can, there's a negative cycle (a loop that keeps getting cheaper forever), and no shortest path actually exists.

Trace on the example graph

Edge list, in order: (0,1,4), (0,2,1), (2,1,1), (1,3,1), (2,3,5). 4 nodes means 3 full passes — but here everything's already settled after the first:

Edge checkedRelax?Running distances
0→1 (4)0+4 < ∞ → yes[0, 4, ∞, ∞]
0→2 (1)0+1 < ∞ → yes[0, 4, 1, ∞]
2→1 (1)1+1=2 < 4 → yes[0, 2, 1, ∞]
1→3 (1)2+1=3 < ∞ → yes[0, 2, 1, 3]
2→3 (5)1+5=6, not < 3 → no[0, 2, 1, 3]

Passes 2 and 3 check every edge again and find nothing left to improve — that's the negative-cycle check passing cleanly. Result: the same dist = [0, 2, 1, 3], same path, same weight 3 as Dijkstra found — as it should, since both are computing the same real quantity, just by different rules.

3

SPFA

Handles negative weightsYes
Findssource → all nodes
TimeO(V · E) worst case, faster in practice
Rust filespfa.rs

Shortest Path Faster Algorithm is Bellman-Ford with one targeted change: instead of blindly re-checking every edge on every pass, it keeps a queue of "nodes whose distance just changed." Only a node's own outgoing edges get re-checked, and only when that node is actually pulled off the queue — so edges that couldn't possibly improve (because nothing upstream of them changed) never get touched. Same worst-case guarantee as Bellman-Ford, same tolerance for negative weights, usually far fewer comparisons in graphs that aren't adversarial.

Trace on the example graph

node 1 (again, dist now 2)1→3: 2+1=3 < 5, dist[3]=3 → re-queued[3]
node 3no outgoing edges[]

Result: dist = [0, 2, 1, 3] — identical to both algorithms above, reached in 6 pops instead of Bellman-Ford's 15 edge checks (3 passes × 5 edges). That gap is the entire point of SPFA: same answer, less wasted work, on graphs where most nodes settle quickly.

4

Floyd-Warshall

Handles negative weightsYes (no negative cycles)
Findsevery node → every node
TimeO(V³)
Rust filefloyd_warshall.rs

The first three algorithms all answer "shortest path from one source." Floyd-Warshall answers a bigger question at once: the shortest path between every pair of nodes, simultaneously. It works entirely on a V×V distance matrix, and its logic is a single, almost suspiciously simple idea, tried for every possible "middle" node k in turn:

The one rule For every pair (i, j): is going i → k → j cheaper than the best i → j route found so far? If so, replace it.

Do that for k = 0, then k = 1, then every other node in turn, and by the time every node has had a turn being the "middle," the matrix holds every pair's true shortest distance — because any real shortest path is just a sequence of such middle-node hops, and this tries all of them systematically.

Trade-off That completeness is also the cost: O(V³) time and a full V×V matrix in memory regardless of how sparse the graph is. Fine for the small graphs this tool visualizes; not what you'd reach for on a graph with 100,000 nodes and only a few edges each — that's Johnson's whole reason to exist.
5

Johnson's algorithm

Handles negative weightsYes (no negative cycles)
Findsevery node → every node
TimeO(V² log V + V·E)
Rust filejohnson.rs

Johnson's answers the same question as Floyd-Warshall — every pair's shortest path — but takes a different bet: on a graph where edges are sparse (E is much smaller than V²), running fast Dijkstra V times beats one slow O(V³) sweep, if Dijkstra could only be trusted with negative weights. Johnson's makes that trade possible in two phases.

Phase 1 — reweight so nothing is negative

Add one temporary node S with a free (weight 0) edge to every real node, then run Bellman-Ford from S — it tolerates negative weights, so this is safe even if the real graph has some. That gives every node v a number h(v): the cheapest cost to reach it from S. Every real edge (u, v, w) is then rewritten as w + h(u) − h(v). That formula isn't arbitrary — it's guaranteed to always land at zero or above, because h(v) can never be more than h(u) + w in the first place (if it were, Bellman-Ford would have routed through u to get a cheaper h(v)). Zero or positive is exactly what Dijkstra needs.

Phase 2 — run ordinary Dijkstra, V times

With every edge now non-negative, plain Dijkstra runs safely from each of the V nodes in turn. Whatever distance it finds just needs one cheap correction to convert back to a real distance: real(u,v) = dijkstra(u,v) + h(v) − h(u).

Worked example — this one needs a negative edge

The main 4-node graph has no negative weights, so reweighting it would be a no-op. Here's a 3-node graph where it actually matters: 0→1 (weight 2), 1→2 (weight −5), 0→2 (weight 10).

Nodeh(v) — cheapest from SCheapest route
00S→0 direct
10S→1 direct
2−5S→1→2 (0 + −5)

Reweighted edges, using w + h(u) − h(v):

  • 0→1: 2 + 0 − 0 = 2
  • 1→2: −5 + 0 − (−5) = 0 — no longer negative
  • 0→2: 10 + 0 − (−5) = 15

Dijkstra on this reweighted graph from node 0 finds dist'[1] = 2, dist'[2] = 2 (via 0→1→2). Converting back — real(0,v) = dist'(v) + h(v) since h(0) = 0 — gives real(0,1) = 2 and real(0,2) = 2 + (−5) = −3. Check it directly: 0→1→2 = 2 + (−5) = −3. It matches, negative total distance and all — something plain Dijkstra could never have gotten right on its own.

6

Yen's k shortest paths

Handles negative weightsNo (built on Dijkstra)
Findsthe k best source → destination paths
TimeO(k · V (E + V log V))
Rust fileyen.rs

Every algorithm so far returns the shortest path. Yen's answers a different question: what are the k best distinct paths between a specific source and destination? The mechanism is almost embarrassingly direct: run Dijkstra to get the best path, delete the edges it used, run Dijkstra again on what's left to get the next-best alternative, and repeat until you have k paths or no path remains at all.

Worked example

This needs a graph with a genuine second option, so the main example gets one extra edge: a direct 0 → 3 route, weight 10 — worse than the main path, but real. Requesting k = 2:

  1. Iteration 1. Dijkstra on the full graph finds 0 → 2 → 1 → 3, weight 3 — same winning path as every algorithm above. Its three edges (0→2, 2→1, 1→3) are removed.
  2. Iteration 2. With those edges gone, node 2 is no longer reachable from node 0 at all, and node 1 has no outgoing edges left. The only surviving route from 0 to 3 is the direct edge, weight 10 — so that becomes path 2.
  3. Iteration 3 would run if k were 3, but by then the graph has nothing left connecting 0 to 3, so Yen's stops early rather than returning a fabricated result.

The shortest of the k paths returned — always the first one found, since each iteration only gets more constrained than the last — is what the app highlights in gold after the animation, exactly like the single-source algorithms.
